# Lightweight frontend and Rust UI options for Dictto

Research date: 2026-10-15. Primary sources only; no local runtime benchmarks or prototypes were run.

## Recommendation

For the current Tauri app, Preact compatibility mode is the first low-change experiment. Plain TypeScript with HTML/CSS removes the framework runtime entirely, but means replacing React's component/state machinery yourself. Svelte is a credible compiled alternative with a larger rewrite. All three still run inside WebView2; shrinking JavaScript does not remove its browser engine/process costs. [Tauri frontend support](https://tauri.app/start/frontend/), [Preact setup](https://preactjs.com/guide/v10/getting-started/), [Preact compatibility differences](https://preactjs.com/guide/v10/differences-to-react/), [Svelte overview](https://svelte.dev/docs/svelte/overview).

For a Windows-only app where a rougher UI is acceptable, ordinary Win32 controls with a small custom recording overlay are the most direct architectural route to removing WebView2. This is an inference from the rendering stacks, not a measured memory ranking. NWG makes the settings form easier; direct `windows`/`windows-sys` bindings give more control and avoid relying on NWG's largely finished toolkit. Egui/eframe is the easiest candidate for a quick all-Rust custom UI; Slint offers a more designed declarative UI. Iced is viable but would not be my first choice for this tiny app.

## Native options

| Option | What actually renders | Fit for Dictto | Maintenance / caveat |
| --- | --- | --- | --- |
| `native-windows-gui` (NWG) | Actual Win32 controls through a wrapper around WINAPI | Strong fit for simple settings, tabs, edits, checkboxes, tray and dialogs; custom drawing for the waveform | Upstream explicitly considers development done and the API mature. Treat this as a stable but low-development dependency; test current Rust/Windows compatibility before choosing it. [Official repository](https://github.com/gabdube/native-windows-gui) |
| Direct `windows` / `windows-sys` + Win32 | OS controls; GDI/Direct2D or a layered bitmap for the overlay | Most control over activation, hit testing, DPI and tray behavior; largest amount of application glue and lifetime/message handling | Microsoft's maintained Rust API bindings, rather than a high-level widget toolkit. Dictto already uses `windows` 0.62. [Microsoft repository](https://github.com/microsoft/windows-rs), [releases](https://github.com/microsoft/windows-rs/releases) |
| `egui` + `eframe` | Immediate-mode, toolkit-drawn widgets in native windows; no HTML/JS browser | Good first prototype for a small utilitarian Rust settings UI and waveform | Active release stream. A native executable is not the same as native Windows controls. Viewport APIs include transparent, topmost, taskbar visibility and mouse passthrough. [Egui repository](https://github.com/emilk/egui), [releases](https://github.com/emilk/egui/releases), [viewport options](https://docs.rs/egui/latest/egui/viewport/struct.ViewportBuilder.html) |
| Slint | Compiled declarative UI, drawn by software or GPU renderers | Better candidate for maintaining a polished custom settings panel without web tech | Actively released (1.18 release in September 2026). Windows uses winit; Fluent/native-looking styling does not make widgets Win32 HWND controls. Slint has changed its default style policy, so pin a version/style intentionally. [Backends/renderers](https://docs.slint.dev/latest/docs/slint/guide/backends-and-renderers/backends_and_renderers/), [style policy](https://slint.dev/blog/default-native-style-change), [release](https://www.slint.dev/blog/slint-1.18-released) |
| Iced | Toolkit-drawn widgets via wgpu or tiny-skia software rendering | Strong Rust state/message model; more framework than this app needs | Official stable docs currently show 0.14.0; upstream calls it experimental. Development docs can be ahead of stable. [Stable README/renderers](https://docs.rs/crate/iced/latest/source/README.md), [releases](https://github.com/iced-rs/iced/releases) |

## Idle repaint and overlay details

Win32 is message driven: process paint requests when Windows invalidates a region, and do not run a polling redraw loop. Egui's immediate-mode API does not inherently require continuous frames: `request_repaint` schedules a new frame, and delayed requests support reducing unnecessary redraws. Iced explicitly models next-frame, timed and no-redraw (`Wait`) requests. These mechanisms permit low idle activity; animations, timers and the application's scheduling determine the result. [WM_PAINT](https://learn.microsoft.com/en-us/windows/win32/gdi/wm-paint), [Egui repaint API](https://docs.rs/egui/latest/egui/struct.Ui.html#method.request_repaint), [Iced redraw requests](https://docs.rs/iced/latest/iced/window/enum.RedrawRequest.html).

For a dictation overlay, preserving the target app's keyboard focus is a functional requirement. Win32 `WS_EX_NOACTIVATE` prevents activation on click; `WS_EX_TOOLWINDOW` hides a tool window from Alt+Tab/taskbar; topmost and layered-window alpha rendering are separate choices. Layered-window mouse passthrough can use `WS_EX_TRANSPARENT`. For a tiny waveform, supplying an alpha bitmap with `UpdateLayeredWindow` is a concrete browser-free rendering route. These APIs do not require changing the speech pipeline. [Extended styles](https://learn.microsoft.com/en-us/windows/win32/winmsg/extended-window-styles), [layered windows](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features#layered-windows).

Egui's `with_active(false)` only specifies initial focus: it is not a documented replacement for permanent Win32 no-activation semantics. Slint exposes its underlying winit window, allowing platform integration, but that still needs an overlay-specific proof of concept. Iced exposes transparent/topmost settings, but these alone do not establish non-activation. Verify show/hide, clicks, hotkeys, focus restoration, DPI and multiple monitors for any chosen toolkit. [Egui viewport](https://docs.rs/egui/latest/egui/viewport/struct.ViewportBuilder.html), [Slint winit accessor](https://docs.rs/i-slint-backend-winit/latest/i_slint_backend_winit/trait.WinitWindowAccessor.html), [Iced window settings](https://docs.rs/iced/latest/iced/window/settings/struct.Settings.html).

## Scope and measurement

A hybrid is possible: keep Tauri settings and use one direct Win32 recording overlay. This removes the overlay's WebView, but retaining a hidden settings WebView still retains browser resources. A full replacement must adapt Tauri-owned commands/state/events/tray/plugins as well as replace the JSX views; local inspection found `AppHandle`, `Emitter` and `State` coupling in backend code.

Do not infer Dictto memory use from toolkit demo figures. Compare release builds on this machine in four states: tray only, settings visible, recording, processing. Record process-tree private memory, idle CPU, active CPU/GPU and wakeups, along with startup time. Evaluate a native overlay first if the always-on overlay is the main concern; evaluate complete native migration only if removing WebView2 is the actual goal.

Microsoft also now documents `windows-reactor`, a declarative WinUI 3 option in preview, and `windows-window`, a small HWND/message-loop helper. Reactor deserves consideration if current Windows-native styling is important, but preview maturity and its default Windows App SDK runtime make it a different tradeoff from classic minimal Win32 controls. A software renderer avoids a GPU rendering stack but does not automatically reduce CPU or total energy use. [Reactor documentation](https://github.com/microsoft/windows-rs/blob/master/docs/crates/windows-reactor.md), [window helper documentation](https://github.com/microsoft/windows-rs/blob/master/docs/crates/windows-window.md).
